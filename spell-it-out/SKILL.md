# Spell it out

One **mechanism**, one **case**, one page read **at a glance**, ending in the **decisions** left open: one, or several about the same mechanism. The reader leaves able to predict what the mechanism does with an input they have not seen, and to answer each question the page asks. The page carries what one look needs; everything found on the way goes in a notes file beside it, linked from the page's details.

A question one function answers in a few sentences gets a chat answer. When the user wants the fix built, hand over to `diagnosing-bugs` after the decision; this skill builds nothing.

| | architecture-report | spell-it-out | diagnosing-bugs |
|---|---|---|---|
| Scope | a whole layer | one mechanism | one bug |
| Ends with | the description | the reader's decisions | a fix, built |

## Process

Investigate fully, show little. Steps 1 to 5 fill the notes file; step 6 draws the page from it.

1. **Pin.** Three lines before reading code: the **mechanism** (entry point to the step that decides the outcome), the **case** (a real input, verbatim or redacted, and where it came from; with no failure, the representative input plus the variant nearest the rule's threshold), the **decisions** the reader must make, each one question with what it blocks ("what would change the outcome" when there is none), and for each the reader's earlier ruling or work it **continues**, with its link ("none" only after searching the records the project keeps). Classify the material ([Sensitivity](#sensitivity)); it decides where every file goes. Done when: the three lines, a continuity link or "none" per question, and the class exist.
2. **Trace.** At one pinned commit (SHA recorded, confirmed on the remote with `git branch -r --contains` before any code link), walk the case from entry to the deciding step: the case's value entering each step, what the step does, `path:line`, and whether a run measured it or you read it. Read the configuration that sets the rule's constants, the test that pins it and the fixture the case came from. Done when: every step has a cite and the case's own value, marked measured or read.
3. **Extract the rule.** The deciding predicate in code form; for each constant its value, where it is set, and measured or placeholder; the case's numbers beside it; the types or fields the predicate reads. Done when: a reader could compute the case's outcome by hand.
4. **Diagnose.** Skip when nothing fails or surprises. Otherwise **ablate** when a reproduction is cheap and permitted: one edit per variant; for the suspect feature, remove it, swap it for a neutral one of the same size, move it; at least two runs each, reported as k of n. The script carries its target and refuses any other, prints each variant's definition beside its result, and records UTC time and cost. Done when: the cause is pinned by a flipping pair, or marked as inferred from reading.
5. **Reach and options.** The **reach**: other inputs (a failing variant no test covers is the first row), call sites, tiers and configurations that run the same rule, the controls in front of it, and who is affected. Then, per decision, two to four **options**, each scored against the same evidence rows with cost and reversibility, "accept" included when legitimate, one recommended. Done when: every reach row cites a run or a `path:line` or is marked unmeasured, and every option is scored.
6. **Render.** Build the page from the notes by following [HTML-FORMAT.md](HTML-FORMAT.md), then screenshot it as `graph-it` says, after the last write, and re-open every cite. Done when: the screenshot shows the flow as a drawn diagram (an `svg` inside the flow part); the first screen at 1280 × 800 holds what HTML-FORMAT.md's First screen rule names for the page's order; a plain-words pass over the answer or questions, the flow labels and the options or explanations finds no identifier or codename, and a component pass over the same finds each named component introduced at first use; a continuity pass finds the page meeting `sync-panel`'s Continuity and Ruled-once rules; no pseudocode line wraps at 390 px; both screenshots were looked at; every cite still says what the page claims, `ls -l` shows owner-only files for sensitive material, and the user has the absolute path, the answer and the decisions asked. When the case was an item on a syncing board, record the path on that item.

## Sensitivity

Material is **sensitive** when it holds an unfixed security weakness, real personal or company data, credentials, or measurements the user keeps private. Then: page, notes, scripts and screenshots go to the private local directory the project names for private material (ask once if none is named), created under `umask 077`, outside any repository; a reproduction reaches only the target named in step 1, and a paid run needs the user's go unless a standing budget covers it; screenshots come from a local headless browser on `file://`; the page loads nothing remote, a diagram library ships as a local vendored copy; nothing about it leaves the machine, and anything written elsewhere calls it "a private worked example" with invented values. Secrets are `<REDACTED>` everywhere, sensitive or not.

Everything else goes where the user asks, else `<tmpdir>/spell-it-out-<mechanism>-<timestamp>.html` with its notes beside it.
