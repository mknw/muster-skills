# Sync panel

The **board** is the one surface where the **owner** (the human) and the **coordinator** (the agent the owner talks to) see what each is waiting on. The coordinator writes it at every **event**; the owner reads it **at a glance** and answers on it, each click reaching the agent that waits on the answer. It replaces status messages: a result left in a terminal never reaches the other party, and state that lives in a file survives a fresh session.

One board, four **states**: **Needs you** (the owner must act), **Running** (a lane works, with a due time and an outcome check), **Loose ends** (a next actor is named, no lane yet), **Done** (the deliverable). One **item** per thing waited on. The issue tracker already shows issues and PRs; the board shows only what the tracker cannot: private items, who moves next, how long each has waited, what unblocks what.

## Find or create the board

The board lives outside every repository, in the directory the project's instructions or the coordinator's memory name for private material; if none is named, ask once. Owner-only access (`umask 077`). It loads nothing remote: a diagram library ships as a vendored copy beside the page. Create what is absent from [BOARD-FORMAT.md](BOARD-FORMAT.md), the helper included.

Done when: the folder is mode 700 and every file 600, `check.py` exits 0, and the helper passes the click Done-when below.

## Events to edits

Every event is one edit, stamped on the item:

| event | edit |
|---|---|
| the owner must decide something | first the auto level's route (Auto level); when it answers owner, item in Needs you with its `category` and `complexity`; the next action names the decision; add the decision context: a brief, the terms, a note on each link, and the AI owner(s) waiting on the answer; at medium complexity or higher, a decision page linked as the title, built with `spell-it-out` when it is about one mechanism (BOARD-FORMAT.md, Decision context, Decision pages) |
| the route answers coordinator | decide on the recommended option now, put the item where that decision points with its decision context, and record it with the edit script's `decided` (Auto level) |
| the owner moves the auto level | run the edit script's `auto` with the level and the newest level click's id, or with the owner's words when they typed it; until then the page shows the click pending |
| the owner overrides an auto decision | undo what the decision started where it can be undone, then run the edit script's `override`, which puts the item back in Needs you |
| a lane is dispatched | item in Running with `due` (dispatch time plus twice the expected duration), `check` (the command that proves the outcome exists) and `lane` (who works it: `term:<handle>` or `herdr:<pane-id>` for an agent with a terminal of its own, `via:<AGENT>` for one without and for any owner-facing agent, `none` while nobody does); all three are required there (BOARD-FORMAT.md, Steering notes) |
| the owner's steering note reaches a lane | take it into the current work, the owner's words governing, and ack when the transport supports receipts; a `via:` agent forwards it word for word to the lane it runs (BOARD-FORMAT.md, Steering notes) |
| a lane reports done | close it: move to Done, the title links the deliverable, the next action goes |
| the owner decides | move the item where the decision points; Done when the decision closes it |
| something is owed and no lane holds it | item in Loose ends, with the next actor and one next action |
| an item blocks or follows another | `rel` on the item (verbs in BOARD-FORMAT.md) |
| items belong together, or are one decision for the owner | a theme record with one next step, and `group` on each member (BOARD-FORMAT.md, The theme) |
| a theme's work is done | close the theme; its id stays taken |
| the owner's answer is a short reply or a choice | `reply`, or `options` with the recommended one, on the item |
| a grill-me click arrives on a Needs-you item | run the grilling round and leave the item in Needs you (BOARD-FORMAT.md, Grill me, The grilling round) |
| a kick-off, grilling-round, de-prio or restore click arrives on a Loose-ends item | do what the click asks and nothing more (BOARD-FORMAT.md, Loose-ends buttons, What the receiving agent does) |
| a lane delivers a report the owner reads and comments on | publish it as the item's report bundle with the edit script's `bundle` command, and set `ai-owner` so feedback has somewhere to go (BOARD-FORMAT.md, Report bundles) |
| the owner's report comments arrive, several in one message | read every comment and reply on the item, by brief, next action or a republished bundle (BOARD-FORMAT.md, Report bundles, What the receiving agent does) |
| the coding agent behind an item needs another answer kind | declare the button on the item (`actions`, BOARD-FORMAT.md, The item) |
| an event names a PR, issue, comment or page | link each one: the title links the primary, every other goes in the item's links row (BOARD-FORMAT.md) |
| an item asks the owner to read a document | link the document itself beside its PR: the file in the worktree that has the PR's branch checked out, fast-forwarded to the PR head first when it is clean, plus a `:LINE[:COL]` link to the section the owner rules on (BOARD-FORMAT.md, Local links); re-point both at the main checkout when the PR merges |
| `spell-it-out` delivers a page for an item | `mechanism` = the page's path |
| a Done item is older than the archive window | move it to the archive page (BOARD-FORMAT.md, The folder) |

An id is never reused, Done and archive included. `changed` is stamped on every edit. A move or close rewrites the opening tag: it sets id, state, actor, since and changed, and carries every other attribute over, so a theme, relations and any attribute added later survive; a close also drops the open-item chips (`due`, `check`, `reply`, `options`, `recommend`), and a move out of Loose ends or a close drops `deprio`. A next action is one sentence naming what the actor does, verb first; on the owner's rows at most 15 words, with the detail in the linked page; an item in Needs you always has one. Edit by anchor: a tool that rejects a stale read rather than applying it, so two agents cannot silently overwrite each other on the one file. The tool holds a board-wide lock across each edit, so a new item's id is assigned inside the same locked edit that inserts it — an agent never reads "the next free number" and writes it in a later step — and an attribute changes through the same anchored tool, never by a read-modify-write of the file. If the tool applies the ops of one patch against the pre-edit line numbers, a move is two patches: cut and paste, then re-read and retarget the state.

Done when: the item reflects the event, `changed` is stamped, and `check.py --stamp` reports 0 flags and no CHECK line reading DONE.

## Auto level

The owner sets one **auto level** for the board, which says which decisions the coordinator may take in the owner's place. Five levels form a ladder, each keeping for the owner a superset of what the next keeps: **off** (the owner takes every decision), **architecture** (keeps architecture, security, changes to the owner's rulings and irreversible actions), **security** (keeps security, ruling changes, irreversible), **only decision changes** (keeps ruling changes and irreversible) and **full autopilot** (keeps irreversible). Every Needs-you decision carries its **category**, one or more of `architecture`, `security`, `changes-ruling`, `irreversible`, or `other` alone (BOARD-FORMAT.md, Auto level).

1. Name the decision's categories. At any level above off, read the project's recorded owner rulings first, and tag `changes-ruling`, citing the ruling, whenever the decision would reverse, supersede or narrow one, and whenever you cannot tell; at only decision changes this check is what still reaches the owner.
2. Ask the edit script's `route` with those categories. It answers from the board's current level, through one table, so every agent and every runtime reads the level the same way; an unknown level reads as off, and an unknown or missing category as the owner's.
3. On `owner`, add the item to Needs you as the events table says.
4. On `coordinator`, the coordinator takes the recommended option now: the item goes where that decision points, keeps its full decision context, and is recorded with `decided`, which re-checks the route inside its locked edit and writes the **auto stamp** (agent, level, option, and the categories it was decided as) and a one-sentence note on which option was taken and why. A stamped item's categories stay as decided.

The level is set only from the owner's click or the owner's words, and the coordinator applies the newest level click only; the edit script refuses an older one. An auto-decided item shows its stamp as a badge, its note, and an **override** button. An override returns the item to Needs you, marked overridden, and the owner decides it from then on. Moving the level changes what comes next; decisions already taken stay until overridden one by one.

Done when: every Needs-you item carries its category, every auto stamp names a level that delegates all of its item's categories, and `check.py` reports no auto flag.

## Reading it for the owner

"What do I have to do": the owner's rows in order, by id, each with its next action; a theme with several of them is one decision, answered with the theme's next step. The owner's rows are every item whose next actor is the owner, whichever state it sits in, except an item in the answered strip, which waits on its AI owner. "What is going on": the counts per state and actor, the oldest open item, anything overdue or stale. Answer from the board; memory of the conversation is not the record. To describe a design, its slices or its status, read its agreed record: the local page linked from its item (a decision or grilling page) together with the owner's comments on it, where the owner has commented; otherwise the latest design the owner agreed, which may be a merged document. The coordinator's own rulings and notes are inputs to that record, never the record.

Done when: the answer cites every id whose actor is the owner.

## Clicks reach the AI owner

The owner answers by clicking a reply, option or declared button, or the default **Done** (BOARD-FORMAT.md, The helper), with an optional note. The **helper**, a small local server bound to the loopback address (BOARD-FORMAT.md, The helper), serves the board and carries the click:

1. The click carries the item id, the answer, the time, the item's version (`changed`) and the note.
2. The helper appends it to the **inbox**, an append-only event log, then sends it in full to each of the item's AI owners through the agents' mailbox system (e.g. Orca), and a notice-only copy to the coordinator, skipped when the coordinator is itself an owner. A mailbox message does not wake an idle agent, so after each delivered owner copy the helper **wakes** that agent's terminal. The routing file selects each agent's transport (BOARD-FORMAT.md, Transports); its guarantees govern receipt and recovery.
3. Each send ends as delivered or failed in the inbox; the page shows sending, sent, seen, not delivered (with retry), answered an older version, and resolved, and a delivered answer steps into the answered strip.

A **steering note** ("include feedback" on a Running item) goes to the agent the item's lane names, the one doing the work. For a `term:` or `herdr:` lane the note travels as a mailbox message to that handle, and a fixed one-line pointer typed into its terminal wakes it to read its mailbox; the note itself is never typed. An idle agent takes the pointer as a prompt at once, and a busy one takes it after its current step. A `via:` lane, an agent with no terminal of its own or any owner-facing agent, gets the mailbox message only and forwards it with its own tool. The coordinator gets its notice.

The helper never writes the board file. An AI owner that receives a click acts on it, then moves the item itself; leaving Needs you is what marks the click resolved. A grill-me click is a request rather than an answer: its AI owner answers with a decision page and leaves the item in Needs you (BOARD-FORMAT.md, Grill me). Report comments travel the same path, every comment of one submit in one message (BOARD-FORMAT.md, Report bundles); their AI owner reads each one, replies on the item and leaves it where it is. The coordinator's notice needs no action. Only offline does a click fall back to the clipboard, and it says so (BOARD-FORMAT.md, The helper).

Saving the helper's code file is a **live deploy** to the owner's running helper (BOARD-FORMAT.md, The helper, Self-reload), gated by nothing beyond a syntax check. Edit and test a copy (another port, a stub mailbox), then move the finished file into place in one step. Tests work on a scratch copy of the board and set the test flag that makes the edit script refuse the real board before reading or writing it. They stop only the processes they started, by recorded PID, never by a name pattern: a pattern also matches the owner's live helper, and killing it ends the owner's session. A worker change reaches the owner with no restart and no new URL; a change to the supervisor itself needs stop, start and a fresh one-time URL for the owner.

Done when (building or changing the helper): a click on a test item lands in the inbox, reaches each AI owner's mailbox (read there, not assumed) and gives the coordinator its notice; the board file's checksum is the same before and after; the page shows sent, seen and resolved across a reload; and a mutation for each baseline requirement is refused, at least: no token 403, a foreign Origin 403, an unknown id 400, `Done` on an item that declares chips 400, a stale version shown as "answered an older version", a reload in the middle of a delivery ending in exactly one copy (and, where the runtime cannot deduplicate prompts, at most one prompt attempt with uncertainty shown, as in Transports), a hostile terminal handle recorded as `wake-failed` with nothing run, and a killed supervisor taking its worker down with `start`, `stop` and `status` all reporting the truth; each report-bundle requirement (BOARD-FORMAT.md, Report bundles) refused by its own mutation; and the Loose-ends buttons refused on any other item (400), an actor the routing file does not list routed to the coordinator, no wake for de-prio or restore, an item id outside the id rule refused (400), and an item with a duplicated section read first-wins; and `grill` refused on any item outside Needs you (400), its owner copy followed by a wake, an AI owner the routing file does not list dropped, an item with none listed routed to the coordinator, a name listed twice sent once, a list over the cap refused (400), and the grill line kept after an edit with no seen copy; and a slider click with no token 403, from a foreign Origin 403, with a level outside the table 400, sent to the coordinator with a wake and shown pending until the board line changes, a body that is not one JSON object 400, a version that is not a `data-changed` stamp 400, a later line at another level shown as superseded, and `override` on an unknown id 400 and on an item with no auto stamp 400, accepted on a Done item that carries one, while any other answer on a stamped item is 400; and a steering note on a `term:` or `herdr:` lane reaching the lane's mailbox followed by one pointer (Herdr's at-most-one attempt guarantee in Transports), on a `via:` lane reaching that agent's mailbox with no wake, refused (400) on an item outside Running, with lane `none` or no lane, on an owner-facing terminal and over its length cap, and a hostile handle in the file recorded as `wake-failed` with nothing run; each by its own mutation.

## The checker

`check.py` reports and never moves an item: it flags the record's defects (the list in BOARD-FORMAT.md), runs every outcome check, and exits 1 on any flag. Prove a new or changed checker with a **mutation run**: plant each defect in a scratch copy and watch each one flagged.

## Rendering at a glance

Position before colour: Needs you is the first section; the owner's rows are tinted wherever they sit, with the next action in full weight; Done is muted. Needs you renders as tiles, each a decision read whole; the other states as one-line rows that expand in place; each section has its own view toggle (BOARD-FORMAT.md, The page). Above the sections, panels that each answer one question the sections cannot; BOARD-FORMAT.md says which form answers each panel's question, and `graph-it` says how that form is drawn.

Verify with a local headless browser on the `file://` URL, and on the helper's page when it runs: the two screenshots `graph-it` names (390 px light, desktop dark) plus desktop light, with one item planted per badge and glyph, a section in each view, a row expanded and the graph overlay open, so every rendering path is seen. Then hand the screenshots to a critic that has not seen the design; apply its layout findings, and take its content findings to the owner.

Done when: the three screenshots have been looked at; 0 remote requests, 0 console errors, scroll width equal to the viewport; every layout finding applied.

## Explain hook

Each open item carries an explain button that copies `Use spell-it-out on sync item <id>: <title>`. Pasted to the coordinator, it runs `spell-it-out` on that item; that skill's own gate decides, so an item with no mechanism behind it gets a chat answer and no `mechanism`. A delivered page's path goes back on the item as `mechanism`, which is what turns the button into the glyph. The button stays a clipboard copy while the helper runs: the helper carries answers to an item's AI owners, and this request goes to the coordinator.
